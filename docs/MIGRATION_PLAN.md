# نقشه راه تبدیل به سرویس‌یاب

## اصول اجرایی

1. تمام تغییرات مهاجرت فقط روی شاخه `serviceyab-rebuild` انجام می‌شود؛ شاخه `main` مرجع دست‌نخورده می‌ماند.
2. پیش از حذف هر فایل، importها، routeها، تنظیمات build و وابستگی‌های native آن بررسی می‌شوند.
3. هیچ migration قدیمی دیتابیس بدون طرح جایگزین و بررسی اثر آن روی محیط‌های مستقر حذف نمی‌شود.
4. هیچ Secret، کلید API، رمز یا داده واقعی نباید در کد یا migration جدید قرار گیرد.
5. تا پیش از تأیید دامنه فاز اول، قابلیت‌های خارج از آن به‌عنوان نیاز قطعی پیاده‌سازی نمی‌شوند.

## فاز یک — جداسازی محصول قبلی

- حذف مسیرها، صفحات، کامپوننت‌ها، storeها و سرویس‌های مختص نامه‌نگاری و تولید متن
- حذف افزونه‌های پرداخت/اشتراک و قابلیت‌های فروش درون‌برنامه‌ای محصول قبلی
- جایگزینی نام، شناسه اپلیکیشن، آیکون، manifest و متادیتای Android
- کنارگذاری API و Edge Function اختصاصی محصول قبلی
- بازبینی و حذف امن migrationهای مختص دامنه قبلی؛ بدون دست‌کاری دیتابیس عملیاتی

## فاز دو — هسته سرویس‌یاب

مدل‌های دامنه، نقش‌ها، مجوزها، چرخه درخواست خدمت و قرارداد API بر اساس دامنه مصوب طراحی می‌شوند. نامزدهای اولیه برای بررسی: مشتری، محصول، درخواست خدمت، نمایندگی، تکنسین، ارجاع، وضعیت گردش کار و سابقه اقدام.

## فاز سه — رابط‌ها و عملیات

پیاده‌سازی تجربه کاربری متناسب با نقش‌ها، داشبوردها، فرم‌ها، جست‌وجو، فیلترها، اعلان‌ها و گزارش‌های موردنیاز فاز اول.

## فاز چهار — امنیت و کیفیت

- سیاست‌های دسترسی مبتنی بر نقش و مالکیت رکورد
- احراز هویت و مدیریت نشست امن
- اعتبارسنجی ورودی‌ها و محدودسازی درخواست‌ها
- تست واحد، یکپارچه و end-to-end
- بررسی build وب و Android و آزمون سناریوهای عملیاتی

## معیار خروج از مهاجرت

- هیچ صفحه یا قابلیت قابل دسترسی از محصول قبلی باقی نمانده باشد.
- هیچ کلید یا رمز پیش‌فرض/افشاشده‌ای در مخزن وجود نداشته باشد.
- مسیرهای اصلی فاز اول با تست قابل تکرار پوشش داده شوند.
- مستندات نصب، تنظیم محیط و استقرار به‌روز باشند.
- Build موفق به‌تنهایی معیار تأیید عملکرد یا امنیت نیست.
